# Windows《三角洲行动》个人乐器自动演奏工具：最终架构方案

审阅日期：2026-09-17。面向单人维护、个人使用、离线优先。本文是开发设计与源码静态复核，未实现产品代码、未运行仓库测试、未操作游戏，也未测得游戏的输入采样周期。除本报告外未修改文件。

**建议新建一个小型 C# / WPF 程序，借鉴三个仓库的局部设计，不直接把任何一个完整项目改造成产品。** 保留本地 MIDI / TXT、单音适配、试听、开始 / 暂停 / 停止、前台保护和诊断。核心原则是：音乐时间先除以倍速，物理约束随后施加；运行时还必须按实际发送完成时刻再次约束，不能仅相信预编译事件表。

## 2. 技术选择与最小分层

推荐 **C#、.NET 10 LTS、WPF、DryWetMIDI、Win32 SendInput、winmm MIDI 试听、System.Text.Json 设置与日志**。仅构建 Windows x64。新项目选择 .NET 10 是为了维护周期；已有仓库的 .NET 8 不必照搬。当前支持状态参考 [Microsoft .NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)。DryWetMIDI 固定一个验证过的版本，不使用浮动包版本。

一个应用项目加一个测试项目足够。应用内部按四个目录分工，不需要四个服务或插件系统：

| 层 | 最小职责 | 禁止跨界 |
|---|---|---|
| Import | MIDI / TXT → Song + 导入诊断 | 不发送输入、不调 UI |
| Core | 选轨、单音归约、映射、物理计划 | 不读窗口、不写磁盘、不依赖 WPF |
| Playback / Windows | 播放会话、时钟、前台、输入、试听 | 不重新解析文件、不决定旋律 |
| UI / Storage | 单窗口、参数、摘要、设置、日志导出 | 不逐音调度、不直接 SendInput |

只为外部边界设置小接口：Clock、ForegroundGuard、InputSink、PreviewSink。由启动入口直接组装，不引入依赖注入框架、事件总线、数据库或通用工作流引擎。

数据流：`文件 / 文本 → Song → Melody → MappedNotes → PhysicalPlan → PlaybackSession → 输出`。试听消费同一计划中最终保留的音符及其实际映射音高，用户听到的是将要演奏的适配结果；首版不做完整原曲合奏试听。

核心数据只需以下几种，使用只读数组或不可变快照；数值时间采用 int64 微秒，运行时转 Stopwatch ticks，避免混淆音乐秒和系统毫秒。

| 数据 | 必要字段 |
|---|---|
| SourceRef | MIDI 的 track / channel / eventIndex / tick；TXT 的 offset / line / column |
| Note | noteId、sourceStartUs、sourceEndUs、pitch、velocity、sourceRef |
| Song | 文件内容 hash、标题、只读 Notes、轨道声道摘要、sourceDurationUs |
| Fingering | 实际 pitch、音键 scanCode、鼠标修饰位掩码；禁止同时低 / 高八度 |
| PlanOptions | 选轨、归约策略、transpose、speed、映射版本、时序参数、冲突策略 |
| PlannedNote | noteId、sourceRef、targetOn / targetOff、plannedOn / plannedOff、Fingering |
| PhysicalEvent | 相对物理 deadline、显式顺序号、noteId、输入种类、down / up |
| Decision | 阶段、原因码、noteId、原值、新值；例如重叠剔除、越界、迟到丢弃 |
| Session | runId、状态、当前音乐位置、取消信号、只读计划、输出实例 |

Song 永远保留原曲；所有适配都创建新结果。无需把每个小字段包装成一套领域类型，但变量、字段、函数名必须带时间单位。输入发送时间与计划时间分别保存。

## 3. 导入与音乐处理

### 3.1 MIDI

首版只接受标准 SMF 0 / 1 和 PPQ。格式 2、SMPTE、RIFF 包装 `.rmi` 明确提示暂不支持，不自动把独立序列合并。文件扩展名只用于筛选，实际检查文件头。

建议上限：MIDI 10 MiB、128 轨、200,000 事件、30,000 成对音符、源曲时长 30 分钟；TXT 1 MiB、30,000 音符 / 休止符、同样时长上限。这些是个人工具的资源边界，不是 MIDI 标准。倍率初限 0.25–2.0，物理成曲最长可达 120 分钟，UI 显示实际播放时长，不能误报仍是 30 分钟。

使用一个文件句柄检查长度并读取有上限的快照。DryWetMIDI 的 `ReadLazy` / `MidiTokensReader` 可逐项读取：在构建完整音符集合前检查事件 / 轨数、取消状态与 chunk 长度，只保留 tempo、轨名、音符事件；忽略的事件也计入资源限额。不可先全量 `GetNotes().ToList()` 再宣称有解析期事件上限。大文本 / SysEx 载荷不积存，长度超限立即报错；分块读取大小不等于载荷总长度上限。参见 [MidiFile 惰性读取 API](https://melanchall.github.io/drywetmidi/api/Melanchall.DryWetMidi.Core.MidiFile.html) 和 [ReaderSettings](https://melanchall.github.io/drywetmidi/api/Melanchall.DryWetMidi.Core.ReaderSettings.html)。

具体规则：

1. 每轨累计绝对 tick，检查加法溢出。保留文件内事件先后顺序。默认 tempo 为每四分音符 500,000 微秒。
2. 收集全文件的 tempo 变化建立全局 TempoMap，不能只看旋律所在轨。相同 tick 的冲突 tempo 按 trackIndex、eventIndex 的稳定顺序取最后一个，并记录警告；tempo=0、非法 PPQ 和损坏结构直接报错。
3. `(track, channel, pitch)` 对应 NoteOn FIFO 队列；velocity=0 的 NoteOn 视为 NoteOff。保留同 tick 原顺序以正确处理重复音；配对完毕后，单音区间处理才使用半开区间 `[start,end)`。
4. 孤立 NoteOff 忽略并计数；未闭合 NoteOn 默认丢弃并定位报告，不擅自延长到全曲结束；零 / 负时长丢弃并报告。不得静默修复成 20 ms，因为最短物理按住属于后续计划层。
5. 音符按全局 TempoMap 换算起止时间，变速跨越长音也必须正确。中间计算保留足够精度，最后统一舍入为整数微秒。
6. 候选分组为轨道 × 声道；默认排除第 10 通道打击乐。首版忽略踏板、弯音、力度控制和音色对游戏的影响，导入摘要明确列出，因此不声称还原原 MIDI 音色 / 表情。
7. 轨名严格 UTF-8 失败后尝试 GBK，再作替代显示并告知；名称解码不改变音乐事件。保留开头 / 结尾休止，首版不自动裁掉。

只容忍不改变音符语义的外围差异，例如有完整 chunk 边界但缺 EndOfTrack 时可警告读完；截断 chunk、非法音高 / 通道、无法恢复边界直接拒绝。DryWetMIDI 容错选项需显式配置，不能“全部 Ignore / SnapToLimits”。官方支持按类型调整读取策略，详见 [MIDI file reading](https://melanchall.github.io/drywetmidi/articles/file-reading-writing/MIDI-file-reading.html)。首版不做“抢救残谱”模式。

### 3.2 TXT 简谱

采用 HarmonicaPlayer 的小文法精神，固定一种节奏语义；不要同时猜测多个网站文法。

- `1–7` 为自然音级，`0` 为休止；默认一拍，BPM 20–300。首版固定 `1=C4`，通过整体半音移调改变调性，并在界面显示。
- `#` 仅修饰后面一个非零音。`【…】` 高一个八度，`(…)` / `（…）` 低一个八度；不可嵌套，闭合符必须匹配。
- 音符后 `_` 减半，最多两次；随后最多一个 `.` 附点；随后每个 `-` / `—` 增加一拍，单个事件不超过 64 拍。比如 `1_.` 为 3/4 拍。
- 空格 / 换行只有排版意义，`|` 是分隔符且终止前音时值修饰。换行不增加延迟。`0` 才产生显式休止；休止符不得加升号或音区修饰。
- BOM 仅允许在文件开头。其他未知字符直接定位到行、列和片段；不自动删歌词、不把非法内容吞掉。UTF-8 / BOM 默认读取，GBK 只在明确选择编码后使用。
- 例：`1 2_ 3_ 5- | 0 【1】 (#4 5)`。导入后统一转 Note / Song；拍数可用 1/8 拍整数单位累计，本规则不需要复杂分数引擎。

不支持反复、连音线、三连音、歌词、多个声部、图片识谱。窗口里附一小段文法说明和示例即可。

### 3.3 轨道与单音旋律

自动推荐只是候选提示：根据旋律名称、音符数量、音域和重叠比例推荐，展示原因，允许用户改选轨道 × 声道。默认选择一个候选，不默认合并全曲。

首版提供两种简单归约：

- **保留起音，默认**：按 start 排序；同一时刻选最高音，同高取力度较大，再按 noteId 决定。后一个新起音截断前一个音的尾部；未选音及被截断尾部不恢复。能避免高音结束后重新冒出伴奏长尾，且每个起音有明确来源。
- **最高活跃音，可选**：扫描所有起止边界，按音高、较新起音、noteId 选胜者；相邻段只有来源 noteId 相同才合并。同音不同 noteId 保留重触发。被遮挡的低音可能恢复，摘要需显示新增切段数。

暂不使用 25 / 60 ms 模糊同刻阈值，避免把快速旋律当和弦；同刻以规范化时间为准。需要处理人工弹奏错位和弦时再添加明确开关，不能偷偷改变默认算法。两种归约均只操作音乐时间，不加 SendInput 安全间隔。

最终旋律必须无重叠、排序稳定，归约规模 `O(n log n)`。物理规划再解决按键放不下的问题，两层不得混成一个无限排队算法。

## 4. 映射与不可演奏边界

InstrumentProfile 保存经校准的基准 MIDI 音高、8 个自然音键 `Z X C V B N M ,`、低 / 高八度鼠标修饰、中键半音方向。当前三个仓库的约定可作为预设，不代表已经验证用户当前游戏版本或乐器。

枚举合法指法构建 `pitch → Fingering[]`，禁止左右八度键同时按下。多指法时优先无鼠标，再按修饰键数量、固定键序选取；首版不做全曲最优指法搜索。逗号键单独验证，不能误用中文标点字符；输出使用扫描码和必要的扩展键标记。

**基准音是实际乐器校准值，不能为提高覆盖率而自动改写。** 整体移调是音乐操作，明确显示半音数；两者不能混为“自动八度”。

映射结果保留原 pitch、移调后 pitch、实际输出 pitch、指法和原因。默认精确映射失败就阻止开始，列出数量和最早几个来源位置。允许用户显式选择“跳过不可演奏音”，保留休止位置。首版不做自动折返或自动移调；界面可提示手动调整方向。移调后超出 MIDI 0–127 同样报错。

## 5. 物理计划：先缩放，再加固定约束

### 5.1 参数与不变量

对选定起点 `P`，音符目标物理时刻为：`targetOn = preRoll + (sourceStart − P) / speed`，结束同理。`preRoll` 是准备修饰状态的前置时间，独立于可见倒计时；首音也必须有足够准备窗口。

之后才使用以下固定物理毫秒参数，**绝不再整体除以 speed**：

| 参数 | 含义 | 建议初始试验值 |
|---|---|---:|
| ModifierSettleMs | 鼠标修饰状态完成最后一次变化，到音键按下的最小间隔；包括从有修饰变为无修饰 | 40 ms |
| MinHoldMs | 成功音键按下后到常规释放的最小间隔 | 45 ms |
| ReleaseGapMs | 前音键释放到下一音键按下的最小间隔 | 20 ms |
| SameKeyUpGapMs | 同一扫描码释放到再次按下的最小间隔 | 45 ms |
| MaxLateMs | 相对该音原始 targetOn 的最大容许迟到 | 50 ms |
| MaxEndOverrunMs | 相对原始 targetOff 的最大尾部延长 | 50 ms |

这些只是开发校准起点，不是游戏测量结论或帧保证。首版只给一个可编辑高级时序配置，别把“60 fps 必定可靠”写成承诺；后续有证据再提供标准 / 稳健预设。重触发必须衡量 **up→down**，不能只检查 down→down。

常规演奏不变量：最多持有一个音键；任何修饰状态改变前先释放音键；down→up 满足 MinHold；up→down 满足对应间隙；修饰状态建立满足 Settle；迟到和尾延长均有限。**停止、暂停、失焦、异常的紧急释放优先于 MinHold**，不为完成一个音继续向失焦窗口等待或发送。

### 5.2 可直接实现的保守槽位算法

首版每个音结束都释放本工具持有的音键和鼠标修饰，下一音再准备指法。这样会限制最快演奏密度，但状态简单、便于证实。连续相同修饰键复用留待有实测收益时再优化。

1. 将所有音乐起止时刻一次性转换成物理目标。保留未经延迟的 targetOn / targetOff 作为本音预算锚点，绝不把上一音迟到加到后续目标。
2. 在前音全部释放以后，尽可能于 `targetOn − Settle` 准备本音修饰。若无需修饰，也要检查距离上次修饰释放是否已稳定。
3. 计算最早可按音键时刻：目标起点、前音键释放 + ReleaseGap、同键最近释放 + SameKeyUpGap、最后修饰状态变化 + Settle 四者取最大。不存在的约束不参与。
4. 结束初值取目标时长的固定 gate（首版内部默认 0.9）。可为下一目标起音预留准备间隙而截短当前音，但不能短于本音实际起点 + MinHold。放不下时保留 MinHold，由下一音的预算决定延迟或跳过；不强行把当前音压成 0。
5. 若本音起点迟到超过 MaxLate，或满足 MinHold 后仍超过 targetOff + MaxEndOverrun，则整音无法放入。默认“保节拍”：跳过该音，保留后续目标时刻；备选“严格”：报告首个冲突并禁止开始。跳过音的修饰事件也不得进入最终计划。
6. 接受本音后登记实际计划释放时刻，再处理下一音。生成事件使用明确顺序号：音键 up、旧修饰 up、新修饰 down、满足间隔后的音键 down。不能依靠枚举容器或排序偶然顺序。

UI 开始前展示“原旋律 N 音，重叠归约移除 A，越界 B，密集跳过 C，延迟 D，最长延迟 E ms”。物理放不下导致的跳过应明确标注，可调慢速度后重编译；不用每次弹确认框。跳过率较高时直接提示原因和首个位置，不假装完整还原。

示例：重复同键的两音目标起点相差 25 ms，MinHold=45、SameKeyUpGap=45，则仅这两项就要求起点至少间隔 90 ms。第二音至少迟到 65 ms，超过 50 ms 时应跳过或拒绝，不能把整段一直推迟，也不能缩小物理间隙凑数。

### 5.3 运行时仍需重验约束

只有计划表正确还不够：线程醒晚后，不能在一个循环里把已经到期的“修饰 down、音键 down、音键 up”连续补发。

- 每次成功发送记录 Stopwatch 的**调用结束时刻**；对于下一次 down，以这些实际时刻重算最早允许时间，保证已请求的物理间隔，不使用名义 deadline 冒充实际发送时间。
- 新音下发前和等待修饰稳定后都重新检查本音迟到 / 尾部预算。若已无可用时长，取消此音剩余事件并释放为它准备的修饰，再处理后续目标；不能只跳过 down 却留下后来会误释放其他音的 up。
- 单次卡顿恢复后，先处理已有持有输入的释放，再批量标记过时音为跳过，绝不突发补齐旧音。音符事件与 noteId / runId 绑定。
- 若已经按下的音因进程卡顿而超过最晚释放期限，醒来立即释放并进入 Faulted；无法倒退修复已发生的长按。明确记录违规实测时长，不伪造成功。
- 实际 down 若比计划晚，应根据实际 down 修正正常最早 up；若修正会越过允许结束预算，在 down 之前就应取消。系统随后再次卡顿属于上一条故障路径。

软件最多保证自己的发送顺序和测量到的调用间隔。SendInput 被 Windows 接收，不等于游戏已采样或已发声；没有游戏帧同步就不能承诺“跨帧必定成功”。

## 6. InputSink、前台保护与生命周期

### 6.1 输入边界

InputSink 只接收物理输入事件并返回成功 / 失败及发送时间；不接受歌曲、不自行决定音符时长。WindowsInputSink 使用扫描码 SendInput，RecordingSink 记录事件供测试。试听输出独立实现 MIDI note on / off，绝不发送键盘或鼠标；两种输出在一次会话内不能切换。

首版每次 SendInput 只发送一个 INPUT，避免不完整批量结果难以精确对账；本工具单音事件量很低，这点调用开销无需优先优化。修饰组合逐项发送并逐项检查。

维护小型持有账本：键 / 鼠标按钮 → `{PendingOrUncertain, Held, downCompletedAt, noteId}`。调用前登记 Pending，返回 1 后标记 Held；若明确返回 0 且调用未成功则撤销该次新增登记并报错；若封装在调用后抛异常、无法确认结果，保留 Uncertain。**账本代表本工具发出的输入及不确定输入，不代表系统或游戏真实物理持有状态。**

统一的 ReleaseAll：先音键，后鼠标修饰；每项独立尝试，成功才移除，失败项保留；重复调用不再释放已清除项，不会新增 down。采用少量有界重试；仍失败则显示具体残留项、禁止新会话、保留“重试释放”入口，不无限重试或静默清空记录。

`SendInput` 受 UIPI 限制；返回值和 GetLastError 不保证能指出 UIPI 原因。报告实际接收数和错误码，权限差异只能作为可能原因，不自动提权或宣称已确认被反作弊拦截。启动前检测本工具使用的音键 / 鼠标键是否已由用户按住，要求先松开，避免接管手动输入。参见 [Microsoft SendInput 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)。

### 6.2 前台目标

倒计时结束时确认用户选择的游戏窗口，保存 HWND、PID、进程身份；不把任意外部窗口自动当目标，也不只比较可变化的标题。每个新 down 前检查目标仍存活且是前台；两个修饰事件之间、修饰和音键之间再次检查。等待长音或休止时也定期检查，建议检查周期上限约 5–10 ms。

失焦后立即取消会话并进入统一释放路径，不自动抢焦点、不自动恢复。释放自己的持有输入不受前台检查阻挡，否则失焦时永远无法松键。前台检查与 SendInput 之间仍存在不可消除的小竞态，报告中应诚实保留此限制；不宣称绝对零误发。

### 6.3 状态与并发

状态足够用：`Idle → Preparing / Countdown → Playing → Pausing / Stopping → Paused / Idle`，失败进入 `Faulted`。UI 控制根据状态启用，不靠多个互相矛盾的 bool 拼接。

- 单一专用播放线程独占输出和账本；UI / 全局热键只投递命令并唤醒取消等待，不从第二个线程释放同一组输入。
- Stop 信号抢占普通命令。只有旧线程结束、ReleaseAll 完成且账本为空，才允许新 Start。runId 用于过滤旧 UI 回调，不能拿它代替等待旧线程退出。
- 暂停立即释放、保存音乐位置和已完成 noteId，恢复前检查前台并重新准备修饰。首版恢复时从下一个尚未开始的音继续，暂停时被中断长音不重吹，界面说明这一语义。
- speed、移调、映射、时序参数只在停止 / 暂停状态修改；重编译剩余计划后恢复。暂停位置存原曲时间，不能用整曲时长比例推断，因为冲突跳过 / 尾延长可能改变计划长度。
- 关闭、停止、暂停、异常、失焦、未来的跳转都调用同一会话终止与释放流程。首版无需进度拖动；将来加入 Seek 时先取消并等待旧会话、释放，再以新音乐起点重编译。
- 线程退出放在 finally；UI 异步等待退出，不能阻塞窗口消息循环。若退出或释放失败，不报告“已停止成功”，保留 Faulted 状态。进程被强杀、系统崩溃时无法承诺 finally 执行，首版不增加常驻守护进程。

## 7. 性能、诊断与本地保存

规划在后台完成，播放开始前冻结计划。导入 / 归约约 `O(n log n)`，映射和计划约 `O(n)`，播放只递增索引；不逐音排序、不扫描全曲、不在播放线程解析 JSON、刷新控件或写磁盘。

调度使用 Stopwatch 单调时钟与绝对 deadline，禁止连续 Sleep(duration) 累积漂移。等待可被取消事件唤醒；先采用有界等待加极短尾部自旋，并测量 CPU / 迟到分布后再决定是否需要 Windows 高精度等待定时器。默认不使用实时进程优先级、持续忙等或全局 GC 禁用。UI 10–20 Hz 刷新快照即可，不给每个输入事件排一次 UI 回调。

诊断至少能回答“哪个音、为什么没有播放、实际等了多久”：

- 导入摘要：源文件 hash、格式、轨道、tempo 数、忽略 / 损坏项目。
- 规划摘要：版本与所有参数、选轨、映射版本、每个被修改音的 sourceRef、原因码、计划起止。
- 运行记录：runId、noteId、目标 / 计划 / 实际发送时间、API 返回值、实际修饰提前量 / 按住 / up→down 间隙、停止原因和释放结果。
- UI 显示总计、最大迟到、分位数和近期错误；阈值使用本次参数，不能写死另一个预设的值。区分“规划跳过”“运行迟到”“发送失败”，更不能把这些计数直接叫“游戏漏音数”。

运行线程写入预分配的有界环形缓冲，后台批量写 JSONL；缓冲满时累计丢弃条数，结束摘要明确记录，不能为了日志阻塞按键。正常结束保存会话摘要，错误 / 用户导出时附详细轨迹与参数快照。日志总量设置小上限，例如轮转保留 5 个各 5 MiB 文件；所有数据留本机，无遥测上传。

设置放 LocalAppData 的单个带 schemaVersion 的 JSON：在同目录写临时文件，flush / 关闭成功后替换目标，保存串行化，关闭时等待未完成保存。保留一份上一版备份足够；损坏时警告并加载默认，不立即覆盖损坏原件。导入文件只读，尚无需求就不建立曲库数据库或持久化编译缓存。

试听先使用系统 MIDI 输出，失败时明确提示设备 / 合成器不可用；游戏演奏仍可使用。不要假定所有 Windows 环境必有可用合成器，也不要为试听立即引入音源下载和音频引擎。试听只能验证适配旋律，不能校准游戏内按键识别。

## 8. 小而够用的开发顺序与验收

### 迭代 A：先验证输入边界

完成单一播放线程、Clock / RecordingSink、状态机和 ReleaseAll，再用少量手工计划接 WindowsInputSink。在专用测试窗口验证组合键与释放，随后在用户实际乐器上校准基准音、鼠标修饰和时序参数。若 SendInput 在目标环境不可用，明确报告；不要先完成庞大 UI 再发现输出路径无效。

### 迭代 B：完成可播放的最小纵向功能

TXT → Song → 精确映射 → 物理计划 → 试听 / 游戏输出；加入开始、暂停、停止、倒计时、全局停止热键和导入 / 运行摘要。此时已经是一个可用的小工具。

### 迭代 C：加 MIDI 和单音适配

加入严格 MIDI 导入、全局 TempoMap、轨道 × 声道选择、默认保留起音归约和可选最高活跃音。把越界与密集冲突显示到同一个检查摘要；配置改动重编译。最后补原子设置保存、日志导出与便携打包。

以下验收均是待开发完成后执行的要求，本报告未声称通过：

| 类别 | 必测用例与通过条件 |
|---|---|
| MIDI | 无 tempo、跨轨变速、长音跨 tempo、同 tick tempo 冲突、velocity=0、同音重叠 FIFO、孤立 off / 缺 off；与人工可算时间表一致，且警告能定位 |
| 导入边界 | 0 字节、假扩展名、截断 chunk、声明超长载荷、PPQ=0、格式 2、SMPTE、超限事件 / 曲长；明确拒绝且 UI 仍可取消，无半成品计划生效 |
| TXT | 合法示例；括号不配对 / 嵌套、`#0`、非法字符、过多 `_`、重复附点、越界时值；行列准确，空格 / 换行不改变时长 |
| 归约 | 同刻和弦、交叉长音、同高重复起音、高音遮挡低音后结束；两种策略结果确定，无重叠，每个输出可追溯 |
| 映射 | 最低 / 最高音、半音、逗号、同音多指法、移调越界；默认失败可见，绝不静默折返或改基准音 |
| 物理计划 | 0.25 / 1 / 2 倍速、短音、同键连打、低→高八度、升号→自然音、首音带修饰；固定毫秒约束不缩放，修饰变化不污染仍按住的前音 |
| 过密段落 | 连续数百音无法全放入时，每个接受音迟到不超预算、结束不超预算，后续目标不累计漂移，跳过数和来源正确 |
| 运行时迟到 | 假时钟注入 8 / 30 / 200 ms 卡顿；从实际发送完成时刻算间隔，不同刻补发，过时音连同附属事件取消，超长已持有音触发释放和故障 |
| 焦点 / 失败 | 开始前、两个修饰事件之间、修饰和音键之间、长音 / 休止时失焦；观察到失焦后不再新增 down，仍尝试所有本工具持有项的 up |
| 输入账本 | 逐个发送失败、调用后异常、逐个释放失败；失败项可重试、ReleaseAll 幂等、账本未清空不能重启，不释放未记录的无关输入 |
| 生命周期 | 倒计时取消、长音暂停 / 恢复、连点开始、快速停开、退出、旧 runId 回调；同时最多一个发送者，停止确认后旧会话不再 down |
| 试听 / 设置 | 试听绝不调用 SendInput；设备缺失可报告；保存失败保留旧文件、设置损坏有提示、无效快照不落盘 |
| 实机 | 用户实际机器的固定游戏版本、固定画质 / 帧率条件，测试短音、同键重复、八度和半音切换；记录试验条件和听到的结果，不能用 API 成功代替发声验证 |

性能验收采用明确环境下的目标而非脱离硬件的硬承诺：参考普通桌面机，10,000 音导入 / 规划以秒级完成、界面可响应；播放不持续占满一个核心；正常负载下停止 / 失焦释放响应以 50 ms 内为目标，记录 p95 / 最大值及失败原因。先记录测量，再调等待策略。30 分钟标准曲播放后线程、句柄和内存不持续增长，日志不无限膨胀。

## 9. 明确不做

不做账号、云同步、在线搜谱、网站、Android、排行榜或分享社区；不做钢琴卷帘、可视化谱面编辑、宏导出、MIDI 硬件实时输入、多乐器合奏、自动乐曲识别或复杂编曲。

首版不做播放中实时改速 / 移调、拖动跳转、循环片段、自动折返、自动修复残缺 MIDI、多套简谱方言、复杂 MIDI 表情还原、自动更新系统、插件架构、数据库和独立后台服务。

不采用进程注入、驱动或规避输入检测的实现。此方案只使用普通 Windows 输入接口；其在当前游戏环境中的可用性与时序参数，以第一轮实机校准为准。

**开发交付的重点只有两条：任何适配都有来源与原因；任何实际发送都受物理时序和统一释放机制约束。** 先把这条最小演奏链做可靠，再根据个人使用中实际遇到的问题增加功能。
